**Goal:** Spec task group 11 in `.kiro/specs/das-client-api/tasks.md`: prove the Phase 4 behaviour that the in-process tests cannot, on the real Compose stack (real RabbitMQ, Redis, Gateway, Managers, Workers): the rate limit is shared by two Gateway replicas (Req 2.4), an event stream survives a Manager kill and delivers exactly one terminal event (Req 7), a new event reaches an open stream within 3 s (Req 7.9), a webhook is retried and its signature verifies (Req 8.6), a budget stops a Request after its first Job (Req 5.7), and `das-client` works against the stack (Req 9.6). The Phase 3 e2e stack (`das-e2e`) is left exactly as it is, as the observability e2e (`das-e2e-obs`) already is, so neither can be disturbed by a Manager kill or a changed Gateway.

## Global Constraints

- **Skip, never silently pass:** the module skips when Docker or Compose is unavailable, exactly like the existing e2e modules, and `DAS_REQUIRE_DOCKER=1` turns that skip into a failure (CI sets it).
- **No cross-clock comparisons.** Docker Desktop's VM clock can differ from the host's. Every latency is measured with the host's own monotonic clock (request sent, frame received), and webhook spacing uses the sink's own timestamps against each other, never against the host or the Gateway.
- **Specified bounds stay specified.** The 3 s of Req 7.9 is asserted as 3 s, with the measured values printed. A flaky assertion is investigated, not widened.
- **Test-only settings stay in the override.** The insecure-webhook flag, the 1 s backoff and the test webhook secret live in files under `tests/integration/e2e/`. `deploy/` is not changed by this group.
- **Every test uses its own Requests** and filters the sink's log by its own Request id; the stack is shared by the module, so order must not matter.
- **Tests first where Docker is not needed.** The sink and the override/config files get Docker-free unit tests (they run in the fast job); the Docker tests are written after a bring-up spike proves the stack starts.
- Quality gates after each task: `uv run ruff check`, `uv run mypy`, `uv run lint-imports`, the touched unit tests. The Docker tests run with `uv run pytest tests/integration/e2e/test_client_api_e2e.py -s`.

## Findings that shape the plan (read from the code, and from the earlier live runs)

- **The existing harness is one module-scoped `Stack`** over project `das-e2e`, with one published Gateway port (`${DAS_GATEWAY_PORT}`), the stub LLM, and a 10 s Manager lease. It has the helpers a new module needs (`compose`, `containers`, `redis_cli`, `lease`, `wait_for`, an agent-registration wait, a `docker kill` takeover). The observability e2e shows the accepted pattern for a different setup: its own project and its own module, with helpers copied rather than shared.
- **Two Gateways do not fit the existing stack.** The `gateway` service publishes a fixed host port, and Compose appends `ports` entries when overriding, so scaling it or overriding it would collide. The plan adds a second service `gateway-b` that `extends` the first with `ports: !override`, each on its own free host port. (`!override` needs Compose 2.24 or later; CI already requires 2.30, and the local Compose is 5.7.) A bring-up spike confirms the merge before any test is written.
- **The Gateway config must change for the e2e keys.** Per-key settings (a rate limit for one key, a default webhook target) are in `client_limits`, which the environment cannot express as a list of overrides. The override mounts an e2e gateway config (`tests/integration/e2e/gateway.client-api.yaml`) instead of `deploy/config/gateway.yaml`: a high default rate for the main key (so no other test is throttled), its webhook pointed at the sink, `allow_insecure_webhooks: true`, `webhook.base_backoff: 1.0`, and a low rate for a second key, matched by its real Key_Fingerprint. The webhook secret is `DAS__WEBHOOK_SECRETS__E2E` (a test literal, in the override only).
- **The stub LLM gives deterministic plans and usage.** For a request it plans one Job per advertised Capability (here `research` and `code-review`, which have no dependencies and are dispatched together) plus a `summarize` Job that depends on all of them. Token counts are `len(prompt) // 4` and `len(reply) // 4`, so they are stable for a fixed prompt. A `[[delay=N]]` marker in the prompt holds a Job in flight for N seconds (both Jobs of a request carry the same marker, so they cannot be given different delays).
- **Planner tokens count against a budget** (`commit_plan` persists the Planner's usage records, and `budget_status` sums every persisted record). So a budget of *the Planner's tokens + 1* is reached by the first Job result and by nothing before it. The test measures the Planner's tokens from an unbudgeted baseline request with the same prompt instead of hard-coding a number, so a change to the stub's arithmetic cannot break it.
- **At that limit both Jobs are already in flight**, because they have no dependencies: Req 5.7 lets in-flight Jobs finish, so the expected end state is both Jobs `Succeeded`, the `summarize` Job `Skipped`, and the Request `Failed` with `error: "budget_exceeded"` (not "one Job ran").
- **The spec gap found in group 10 applies here:** the API returns `final_result` only for a `Completed` Request, so "partial results visible" (design, Testing Strategy) cannot be asserted through `GET /v1/requests/{id}`. See Decision 1.
- **What the earlier live runs already showed** (real Redis, the real CLI, by hand, not as tests): blocking-read SSE works against a real Redis; a signed webhook with retries is delivered and verified; `429`s for the rate limit, quota and stream cap. Those runs de-risk the stack, but they ran without Managers, Workers or RabbitMQ, so they do not replace these tests.
- **Cost of a first run:** the stack needs `rabbitmq:4.1-management`, `redis:7.4` and `python:3.12-slim` (pulled; the registry is reachable from here) and builds three images (`das-gateway`, `das-manager`, `das-worker`) with `pip`. That is a few minutes and a few hundred MB on your machine. It happens at the spike (Task 2).
- **CI:** the e2e job already runs `uv run pytest tests/integration/e2e` (so the new module is picked up), and its log collection and teardown loop over `das-e2e das-e2e-obs`, which must gain `das-e2e-client`. The job's step timeout is 24 minutes; the new stack adds an estimated 4 to 6 minutes and is measured in Task 6.

## Decisions (recommendation first; say if you want a different one)

1. **The budget-stop test asserts what the API shows** (the Request's status and error, each Job's state, the `budget` object, no `final_result`), not "partial results", and the API is left unchanged. If you would rather expose results for a budget-stopped Request, that is a spec change (Req 5.9 and Req 11.1 conflict as written) and a separate piece of work before this test can say "visible". This plan assumes the first.
2. **A separate project and override** (`das-e2e-client`, `docker-compose.client-api.e2e.yml`) instead of editing the shared `docker-compose.e2e.yml` that the Phase 3 tests use. Cost: a third stack bring-up in the e2e job.
3. **Two Gateways as two services** (`gateway` and `gateway-b`, one `extends` of the other), not `--scale gateway=2` with a host-port range: the ports are then known to the test instead of being discovered.
4. **An e2e Gateway config file** mounted over `/etc/das/config.yaml`, not environment variables (the env cannot express the per-key override list).
5. **Negative controls are manual and temporary.** The fixture reads an optional `DAS_E2E_CLIENT_OVERRIDE_EXTRA` path (a further Compose file) so a deliberately broken variant can be layered on without touching the committed files; the controls are run once, reported, and not committed as tests.

## Risks and open points

- **Timing assertions on real infrastructure.** The 3 s bound of Req 7.9, the webhook spacing and the takeover are the likely sources of flakiness, especially on a loaded CI runner. They are measured with a single clock, printed, checked three times in Task 5, and investigated rather than widened. Webhook spacing bounds allow for the sender's polling interval (up to 1 s).
- **First-run cost and local state.** The stack leaves images behind (three built, three pulled) and uses ports; the fixture tears down with `down -v` and the free ports are chosen per run. The spike asks first.
- **CI minutes.** A third stack in the e2e job; measured in Task 6.
- **`extends` plus `!override`** may not merge as expected on every Compose version; CI requires 2.30, and the spike is where this is found, with the `--scale` fallback ready.
- **The e2e job cannot be fully verified locally** for GitHub-specific behaviour (runner resources, timing); the first run on GitHub is the real test of the job-level timeouts.
- **Spec gap (Decision 1):** until Req 5.9 and Req 11.1 are reconciled, "partial results visible" is not testable.
- **Not planned:** load or soak tests, a third Gateway, TLS webhooks (the real `https` path needs certificates; the unit tests cover the URL rules), a Grafana or Prometheus check of the new metrics (the observability profile is a separate stack), and changing the Phase 3 e2e stack.
